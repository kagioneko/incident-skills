# インシデントレスポンス（保全・分析）

## 0. このスキルの範囲

**やること**: 証拠の保全、読み取り、分析、報告
**やらないこと**: 削除、移動、書き換え、実行

削除が必要になったら、ユーザーに `incident-cleanup` スキルの明示的な呼び出しを求めること。
本スキルから削除処理へ自動的に進んではならない。

---

## 1. 前提条件（満たされない場合は分析を開始しない）

作業を始める前に、以下のディレクトリ構成が成立しているか確認する。
成立していなければ、**分析を開始せず、まずこの構成を作るようユーザーに提案する。**

```
evidence/
├── original/       # 原証拠。読み取り専用。書き込み・削除ともに不可
├── working-copy/   # 分析・展開・復号用。書き込み可
├── reports/        # 報告書の出力先。書き込み可
└── audit/          # 操作履歴の記録先。追記のみ
```

エージェントに渡す作業ディレクトリは `working-copy/` `reports/` `audit/` のみ。
`original/` は理想的には作業範囲の外に置く。見えても書けない状態にする。

### 読み取り専用化の手段（強度順）

| 強度 | 手段 |
|---|---|
| 強 | ディスクイメージ化して `mount -o ro,loop` / VHDX を読み取り専用マウント |
| 中 | NTFS ACL / POSIX ACL で書き込みを明示的に拒否 |
| 中 | `chmod -R a-w`（rootからは解除可能） |
| 弱 | Windowsの読み取り専用属性（権限のあるプロセスから解除できる。境界ではなく目印） |

> [!IMPORTANT]
> 「読み取り専用属性を付けた」は保証ではない。**強度を理解した上で選ぶこと。**
> この前提条件が満たせない環境では、その旨を明示してから分析に入る。

## 2. 防御の層

このスキル（SKILL.md）は**判断方針**であって、強制力ではない。
実際の保証は下の層が担う。上ほど強い。

```
Layer 0  OSレベルの読み取り専用マウント     ← 物理境界
Layer 1  サンドボックス
Layer 2  permissions の deny ルール
Layer 3  PreToolUse フック（終了コード2で遮断）
Layer 4  SKILL.md の判断規則               ← ここ（お願い）
Layer 5  全操作の監査ログ
```

> [!CAUTION]
> `allowed-tools` は「そのツールを確認なしで使える」設定であり、
> **それ以外のツールを禁止するものではない。**
> ツールを実際に制限するには deny ルールまたは PreToolUse フックを使う。
> 設定例は `references/hardening.md` を参照。

## 3. Phase 1: 収集（Collect）

**原則: 消す前に全部取る。読む前に全部コピーする。**

`scripts/collect_evidence.sh` を使う。手で集める場合も、以下の順序を守る。

### 収集順序は「揮発性の高い順」（RFC 3227 の原則を、本スクリプトで扱える範囲に落としたもの）

1. プロセス・ネットワーク接続（`ss`, `ps`, `lsof`）
2. ログインセッション（`w`, `last`, `lastb`）
3. ディスク上のログ・認証情報・設定
4. 永続化ポイントとファイルタイムライン
5. 凍結・マニフェスト・パッケージング

> [!NOTE]
> **物理メモリの取得は本スクリプトの対象外。**
> 揮発性の観点では優先度が高いが、環境依存性と侵襲性が大きいため実装していない。
> メモリ証拠が必要な場合は、ホストを停止せずネットワーク隔離し、
> 外部からメモリイメージを取得すること。

> ディスク上のログは待ってくれる。プロセスとネットワーク接続は秒単位で消える。
> 数百MBのログをコピーしている間に攻撃者のセッションが切れる。

### 収集先

`/var/tmp` 配下に `mktemp -d` で作成し `chmod 700`。`umask 077` を先に設定する。

- `/dev/shm` は**使わない**（tmpfs でメモリを消費、容量制限、noexec の場合あり、再起動で消失）
- 専用の外部ストレージ・証拠用ボリュームが使えるならそちらを優先

### 収集対象（`references/evidence_checklist.md` に詳細）

- システムログ（auth.log, syslog, nginx, apache, docker）
- ユーザー・認証（passwd, shadow, group, 全ユーザーの `.ssh/` と履歴系）
- **AIエージェントのセッションログ**（`~/.claude/projects/`, `~/.codex/`, `~/.gemini/`）
- **`authorized_keys` の全探索**（ホームディレクトリの外に置かれる場合がある）
- **`sshd -T` による実効設定**（`AuthorizedKeysFile` は変更できる）
- SUID/SGID バイナリ
- 永続化ポイント（cron, at, systemd timers, `ld.so.preload`, `sudoers.d/`, シェル初期化ファイル）
- MAC タイムライン

### 完全性の記録

- 証拠ディレクトリ内の全ファイルの SHA-256 マニフェスト（**相対パスで**、マニフェスト自身は除外）
- アーカイブ自体のハッシュ
- **ハッシュを同じサーバー上だけに置かない**（root を取られていれば両方書き換えられる）
  ※ 検証できるのは「収集後に証拠セットが変化していないこと」まで
- 回収後に調査端末側で再計算して一致を確認し、別端末・パスワードマネージャーのセキュアノート・
  改変困難な外部ストレージへ記録する。可能なら調査端末の秘密鍵で署名する

## 4. Phase 2: 分析（Analyze）

**原則: 何も消さない。何も動かさない。何も実行しない。**

### 絶対ルール

> [!CAUTION]
> 1. **証拠ファイルは「テキストとして読む」だけ。絶対に実行しない**
>    - `.sh` `.py` `.js` などは表示のみ。`source` `bash` `python` `node` で実行しない
>    - バイナリは `file` で種別確認のみ
>    - crontab / systemd unit は読むだけ。`reload` `restart` しない
>    - 理由: 攻撃者がスクリプトに仕込んでいる可能性がある
> 2. **分析フェーズでは一切ファイルを削除しない**
> 3. **「Continue」は分析続行の意味であり、削除の許可ではない**
> 4. **「消せる？」は質問であり指示ではない。必ず確認を返す**
> 5. **読まずに判断しない。読まずに消すのは禁止**
> 6. **原証拠（`original/`）には一切書き込まない。作業は `working-copy/` で行う**

### 不審ファイルの表示方法

ログやファイルに制御文字・端末エスケープシーケンスが含まれていると、
端末表示の改変、文字列の隠蔽、クリップボード操作などが起こり得る。

**推奨:**
- `cat -v`
- `sed -n 'l'`
- `xxd`（バイト列の確認）
- エスケープ処理を行う専用パーサー

**初回確認に使わない:**
- 生の `cat`, `echo`, シェル展開による端末出力
- `less -R` / `less -r`（制御シーケンスを通す）

### 分析チェックリスト

```markdown
## 侵入経路
- [ ] auth.log: Accepted publickey / password の送信元IP
- [ ] /etc/passwd: UID 0 が root 以外にいないか（awk -F: '$3==0')
- [ ] bash_history: usermod, useradd, wget, curl, nc, chattr
- [ ] all_authorized_keys.txt: ホーム外の authorized_keys
- [ ] sshd_effective_authkeys.txt: AuthorizedKeysFile が変更されていないか
- [ ] cron / at / systemd timers: 不審な定期実行
- [ ] SUID/SGID: ベースラインとの差分

## AIエージェントの関与
- [ ] ~/.claude/projects/*.jsonl の "type":"assistant" 側に
      該当コマンドの tool_use があるか
      （"type":"user" 側は「ファイルを読んだ結果」なので実行の証拠にならない）
- [ ] settings.json の deny / allowedTools
- [ ] ※ Bash ツール経由の実行は、非対話シェルを使う構成では
      .bash_history に記録されない（製品・実行方法により異なる）

## 漏洩範囲
- [ ] .env / config 系の API キー・トークン
- [ ] .ssh/: 秘密鍵・authorized_keys・known_hosts
- [ ] bash_history: コマンドラインに直書きされたトークン
- [ ] mysql_history / psql_history
      ※ MySQL の履歴は _HiStOrY_V2_ 形式でスペースが \040 に
        エスケープされる。素の grep では引っかからない。デコードしてから走査する

## 時系列
- [ ] timeline_mac.txt: 侵入前後に更新されたファイル
- [ ] .bash_history のタイムスタンプ有無（HISTTIMEFORMAT 未設定なら日時なし）
      ※ 履歴の並び順は実行順ではない。シェル終了順に追記される
```

### 結論の書き方

**事実と推測を分離する。** 各所見に確度を付ける。

- **確定**: ログに直接記録されている
- **強く示唆**: 複数の独立した記録が整合している
- **可能性**: 一つの記録からの推測
- **判定不能**: 必要な記録が存在しない

> [!IMPORTANT]
> 「ログに記録がない」は「起きていない」ではない。
> ひとつのレイヤーの証拠から、隣のレイヤーの結論を出さないこと。

### 3兄弟共通の報告ルール

すべての報告で、以下の3項目を**必ず併記する。**

| スキル | 併記する3項目 |
|---|---|
| **incident-response** | 確認した証拠 / 存在しない証拠 / 確認不能な証拠 |
| incident-containment | 実施した封じ込め / 残存する経路 / 未失効の権限 |
| incident-cleanup | 削除した対象 / 残した対象 / 原証拠の保全場所 |

**「安全です」「問題ありません」と断定しない。**
断定できるのは「確認した範囲では」までである。

```
❌ バックドアはありませんでした
⭕ 今回確認した永続化ポイントの範囲では、追加のバックドアを示す所見は
   確認できませんでした。カーネル・メモリ・クラウド管理プレーンは
   別途確認が必要です。
```

## 5. Phase 3: 報告と対応（Report）

1. `templates/forensic_report.md` で報告書を作成（`reports/` へ出力）
2. `templates/credential_rotation.md` でローテーション対象を洗い出す
3. コード修正（0.0.0.0 バインド等）は**ユーザー承認後**に実施
4. 削除が必要な場合は、**ユーザーに `incident-cleanup` の明示的な呼び出しを求める**

### ローテーション対象で忘れられがちなもの

- TLS 証明書と対応する秘密鍵（`certbot revoke --reason keycompromise` のあと再発行・再配備まで）
- 停止したサービスの DNS A レコード（ダングリング DNS）
- known_hosts に載っていた接続先ホスト
- コマンドラインに直書きした PAT（`git clone https://user:token@...`）

## 6. 収集スクリプトの信頼性について

`scripts/collect_evidence.sh` は**侵害ホスト自身のコマンド**（bash, ps, ss, find）を
使って動作する。ルートキットが導入されている場合、**収集結果自体が偽装されている
可能性がある。**

確実な保全は、ホストを停止してディスクイメージを外部から取得すること。
クラウドであれば管理プレーンからのスナップショットを優先する。

### キットの配置方針（ハイブリッド）

| 時期 | 方針 |
|---|---|
| 平時 | 署名済みキットを手元・GitHub・安全な保管場所に置く（**これが正本**） |
| 平時（任意） | サーバーにも配置してよいが、**正本とはみなさない**（可用性のためのキャッシュ） |
| 有事 | 可能なら調査端末から正本を転送。転送後にハッシュ照合してから実行 |
| 有事 | 管理プレーンのスナップショットを優先。ホスト上の結果は参考情報として扱う |

サーバー上のキットは、**手元の正本とハッシュが一致した場合のみ使用可能**とする。

> [!NOTE]
> 隠蔽は防御ではない。`/opt/.incident-kit` のようにドット始まりで隠しても、
> root を取られた時点で無価値になる。それは攻撃者と同じ手口でもある。
> 隠す機能を足すより、限界を明示するほうが価値がある。

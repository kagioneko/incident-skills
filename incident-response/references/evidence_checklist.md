# 収集対象チェックリスト — なぜそれが要るのか

各項目について「**取れないと何が言えなくなるか**」を書いている。
収集を省略する判断は、この列を読んでから行う。

---

## Phase 1: 揮発性データ（最優先）

**取得コストは数秒。遮断・再起動・時間経過で消える。**

| 対象 | コマンド | 取れないと |
|---|---|---|
| ネットワーク接続 | `ss -tunap` | **誰と通信していたかが永久に分からない**。C2 の特定ができない |
| 待受ポート | `ss -tlnp` | どのサービスが外部に開いていたかが分からない |
| プロセス一覧 | `ps auxfww` | 実行中のマルウェアを見逃す。親子関係から侵入経路を辿れない |
| オープンファイル | `lsof -n -P` | プロセスが掴んでいたファイル・ソケットが分からない |
| **削除済みバイナリで実行中** | `ls -l /proc/*/exe \| grep deleted` | **マルウェアの典型的な痕跡を見逃す**。ディスクを調べても本体が存在しない |
| ファイアウォール | `iptables -L -n -v` | 攻撃者がルールを変更したか判定できない |
| ログイン中セッション | `w` / `who -a` | 侵害中に誰が入っていたかが分からない |

> [!IMPORTANT]
> **封じ込めの前に取る。** 遮断した瞬間に接続情報は消える。
> 数秒のコストで、後から絶対に取り戻せない情報が残る。

---

## Phase 2: ログインセッション履歴

| 対象 | 取れないと |
|---|---|
| `last -a -F` | 過去のログイン元 IP・時刻が分からない |
| `lastb -a -F` | ブルートフォースの試行が分からない。攻撃の開始時刻を推定できない |
| `lastlog` | 各アカウントの最終ログインが分からない。休眠アカウントの悪用を見逃す |
| `loginctl` | systemd-logind 管理下のセッションが分からない |

---

## Phase 3: システムログ

| 対象 | 取れないと |
|---|---|
| **`auth.log` / `secure`** | **SSH ログインの成否・接続元・使用鍵が分からない**。root 侵害の判定に最も直接的な証拠 |
| `syslog` / `messages` | サービスの異常・再起動の記録が分からない |
| `kern.log` | カーネルレベルの異常（OOM・モジュールロード）が分からない |
| `fail2ban.log` | 遮断された試行の記録が分からない |
| `dpkg.log` | 攻撃者がインストールしたパッケージが分からない |
| Web サーバーログ | HTTP 経由のアクセスが分からない |
| Docker ログ | コンテナ内の挙動が分からない |
| **journald の永続化状態** | **「ログが無い」のか「最初から保存されない設定だった」のかが区別できない** |

> [!NOTE]
> `/var/log/journal` が存在しなければ journald は揮発設定であり、
> **再起動時点で過去のログは消えている。**
> これは「取得失敗」ではなく「そもそも存在しない」という所見になる。
> 本スキルはこれを `journal_storage.txt` に明示的に記録する。

## Phase 4: 認証・ユーザー

| 対象 | 取れないと |
|---|---|
| `/etc/passwd` | **UID 0 のアカウントが root 以外に存在するか判定できない** |
| `/etc/group` | 特権グループ（sudo / wheel / docker）の所属が分からない |
| `sudoers` / `sudoers.d` | 権限昇格の設定変更を見逃す |
| `sshd_config` + `Match` ブロック | 特定ユーザーだけ設定を変える手口を見逃す |
| **`sshd -T` の実効設定** | **`AuthorizedKeysFile` が変更されていた場合、鍵の探索先を間違える** |
| `pam.d` / `nsswitch.conf` | 認証をすり抜ける PAM モジュールの挿入を見逃す |
| **`authorized_keys` 全探索** | **ホームディレクトリ外に置かれたバックドア鍵を見逃す** |
| 各ユーザーの `.bash_history` | 実行されたコマンドが分からない |
| `.mysql_history` / `.psql_history` | DB 操作と、平文で残ったパスワードが分からない |
| `known_hosts` | **どのホストに接続していたかの名簿**。侵害範囲の特定に使う |
| シェル初期化ファイル | ログイン時に実行される永続化を見逃す |

> [!CAUTION]
> **`~/.ssh/` と `/home/*/` だけでは足りない。**
> 実例として、`/usr/.system/.ssh/authorized_keys` に置かれたバックドアがある。
> `find / -xdev -type f -name 'authorized_keys*'` が必須。
>
> さらに `AuthorizedKeysCommand` は、鍵をファイルではなく**外部コマンドの出力**から
> 取得する設定であり、ファイル検索では原理的に見つからない。

### 秘密情報の扱い

`/etc/shadow`・SSH 秘密鍵・認証トークンは、**本文を収集しない。**
存在・パス・権限・サイズ・mtime・SHA-256 のみを `inventory/` に記録する。

| 判断 | 理由 |
|---|---|
| 本文を取らない | 侵害ホスト上に平文の認証情報詰め合わせを作らない。`chmod 600` は root に無意味 |
| 指紋は取る | 「その鍵が存在した」「いつ更新された」「他所で使われた鍵と同一か」は判定できる |

本文が必要なら、ホスト停止後のディスクイメージ取得か、クリーン端末への直接ストリーム。

## Phase 5: AI エージェントのセッションログ

| 対象 | 取れないと |
|---|---|
| `~/.claude/projects/*.jsonl` | **エージェントが実行したコマンドが分からない** |
| `~/.codex/` `~/.gemini/` 等 | 同上 |
| エージェント設定（`settings.json` 等）の deny / allowedTools | 何が許可されていたかが分からない |

> [!IMPORTANT]
> **これが実行者の特定に決定的になることがある。**
>
> エージェントの Bash ツール経由の実行は、**非対話シェルや子プロセスを使う構成では
> 通常の `.bash_history` に記録されない。**
> 製品や実行方法によって挙動は異なるため一般原則として断定はできないが、
> 実際にこの差が「履歴にある = 対話的に実行された」という切り分けの材料になった。
>
> 逆に、セッションログの `"type":"assistant"` 側に該当コマンドの `tool_use` があれば、
> エージェントが実行したことになる。
>
> 実例として、この区別により「AIエージェントが実行した」という仮説を
> 検証・否定できたケースがある。
>
> **エージェント別にディレクトリを分けること。**
> 同じ名前のファイル（`settings.json`・`projects/`）が複数のエージェントに存在するため、
> 同一ディレクトリへ集めると上書きが起き、証拠と来歴の両方が失われる。

## Phase 6: 永続化ポイント

| 対象 | 取れないと |
|---|---|
| cron / `cron.d` / spool | 定期的な再感染を見逃す |
| `at` ジョブ | 一回限りの遅延実行を見逃す |
| systemd units / timers | 常駐バックドアを見逃す |
| **`ld.so.preload`** | ライブラリ差し替えによる隠蔽を見逃す |
| `rc.local` / `init.d` | 起動時実行を見逃す |
| `/etc/profile.d/` | 全ユーザーのログイン時実行を見逃す |
| **SUID/SGID** | 権限昇格の踏み台を見逃す |
| パッケージ整合性 | 改ざんされたシステムバイナリを見逃す |
| カーネルモジュール | ルートキットの手がかりを失う |
| **MAC タイムライン** | **`auth.log` が無い場合、侵入時刻を推定する唯一の手段** |

> [!NOTE]
> `-perm -4000 -o -perm -2000 -type f` は**括弧が必要**。
> 括弧なしだと `-o` の優先順位により `-type f` が SGID 側にしか適用されない。
>
> タイムラインは A（アクセス）・M（更新）・C（メタデータ変更）の3つを取る。
> `%T@` だけでは M しか取れない。

## Phase 7: 収集ギャップの記録

**「取れなかった」を記録しないと、後から
「そのファイルは存在しなかった」のか「取得に失敗した」のかが区別できない。**

| 区分 | 意味 | 分析での扱い |
|---|---|---|
| `missing` | 対象が存在しなかった | **それ自体が所見**（例: auth.log が無い = ログが取られていない） |
| `failed` | 取得を試みたが失敗した | 再取得の余地がある。所見としては使えない |
| `skipped` | 意図的に収集しなかった | 必要なら別手段で取得する |

## Phase 8: 完全性

| 対象 | 取れないと |
|---|---|
| `MANIFEST.sha256`（相対パス） | 回収後に照合できない。改変検出ができない |
| アーカイブの SHA-256 | 転送中・保管中の改変を検出できない |
| `COLLECTION_METADATA.txt` | 誰が・何を使って・いつ取ったかが分からない |
| collector 自身の SHA-256 | 収集ツールが改変されていないか確認できない |

> [!CAUTION]
> **ハッシュを同じサーバー上だけに置かない。**
> root を取られている場合、攻撃者はアーカイブとハッシュの両方を書き換えられる。
> 生成直後に、別経路（スマートフォンのメモ、パスワードマネージャー、別端末）へ退避する。
>
> なお、これで保証できるのは「**収集後に証拠セットが変化していないこと**」であり、
> 侵害ホスト上で生成した時点の真正性までは保証できない。

---

## 手動確認が必要な範囲（ホスト内から検出できない）

クラウド管理プレーンは、どれだけホスト内を調べても見えない。
`persistence_hunting.md` の Tier 3 チェックリストを、**人間が手で**実施する。

- IAM ユーザー / アクセスキー / サービスアカウントキー
- IAM ロール・信頼ポリシーの変更
- **`startup-script` / `user-data`**（汚染されていると再構築しても復活する）
- スナップショット / AMI の他アカウントへの共有
- 監査ログの無効化、保存先の変更
- 未使用リージョンでのリソース作成

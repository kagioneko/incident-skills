# 認証情報ローテーション チェックリスト

> [!CAUTION]
> ### 失効・再発行は必ずクリーンな端末から行う
>
> 侵害された環境で、新しい API キー・パスワード・SSH 秘密鍵を
> **作らない、置かない、貼らない。**
>
> まだ root を取られているなら、**新しい鍵も即座に漏れる。**
> 新しい鍵の配備は、**新環境を構築してから。**

> [!IMPORTANT]
> ### 「失効」は3段階ある。1つでも抜けると意味がない
>
> 1. **失効** — 古い認証情報を無効化する
> 2. **再発行** — 新しい認証情報を作る
> 3. **再配備** — 新しい認証情報を使う側に反映する
>
> よくある失敗は、再発行して安心し、**古い方を失効させていない**こと。
> TLS 証明書が典型で、「新しい証明書を入れた」だけでは、
> 盗まれた秘密鍵に対応する古い証明書は有効なままである。

## 1. SSH 鍵

- [ ] 侵害ホストにあった秘密鍵を特定（`inventory/` の指紋一覧から）
- [ ] **その公開鍵が登録されている全ホストの `authorized_keys` から削除**
      ※ 自分のサーバーだけでなく、GitHub / GitLab / 他社サービスも
- [ ] GitHub / GitLab の SSH キー一覧を確認
- [ ] **Deploy Key**（リポジトリ個別の鍵）を確認 ← 見落としやすい
- [ ] 新しい鍵をクリーン端末で生成
- [ ] 新環境に配備

```bash
# 登録済み公開鍵の一覧（GitHub）
# https://github.com/settings/keys
# Deploy Key は各リポジトリの Settings > Deploy keys
```

> [!NOTE]
> `authorized_keys` を `>` で上書きしても、**ホームディレクトリ外に置かれた
> `authorized_keys` は消えない。** `find / -xdev -name 'authorized_keys*'` の結果を確認すること。

## 3. DB 認証情報

- [ ] `.mysql_history` / `.psql_history` に含まれるパスワード
      ※ MySQL の履歴は `_HiStOrY_V2_` 形式でスペースが `\040` にエスケープされる。
        `grep "IDENTIFIED BY"` では引っかからない
- [ ] アプリケーションの設定ファイル / 環境変数
- [ ] `@'localhost'` に限定されているか確認（リモート接続可能なら優先度が上がる）
- [ ] パスワード変更
- [ ] アプリ側の設定を更新して再起動

```sql
-- 変更後、権限の再確認
SELECT user, host FROM mysql.user;
SHOW GRANTS FOR 'user'@'host';
```

## 4. TLS 証明書 ★最も見落とされる

> [!CAUTION]
> **証明書の秘密鍵が漏洩した場合、証明書を「失効」させる必要がある。**
> 新しい証明書を入れるだけでは、**盗まれた鍵に対応する古い証明書は有効なまま**で、
> 中間者攻撃に使える。

- [ ] 侵害ホストにあった秘密鍵を特定（`/etc/letsencrypt/` `/etc/ssl/private/` など）
- [ ] **失効**（理由コードは `keycompromise`）
- [ ] 旧鍵を破棄
- [ ] 新しい鍵で再発行
- [ ] 新環境に再配備
- [ ] **certbot の管理設定も削除**
      ※ 残っていると、次の `certbot renew` が失効済み証明書を更新しようとする
- [ ] 証明書透明性ログ（crt.sh）で、把握していない証明書がないか確認

```bash
certbot revoke --cert-path /etc/letsencrypt/live/example.com/cert.pem \
               --reason keycompromise
certbot delete --cert-name example.com
```

```
CT ログの確認: https://crt.sh/?q=example.com
```

## 5. クラウド IAM ★ホスト内からは検出できない

> [!CAUTION]
> **OS 側のバックドアを全て除去しても、IAM に管理者キーが残っていれば再侵入される。**
> ここを確認せずに「対応完了」としない。

- [ ] IAM ユーザーが増えていないか
- [ ] 既存ユーザーにアクセスキーが追加されていないか
      （キーの「最終使用日時」と「使用リージョン」を確認）
- [ ] サービスアカウントキーの新規発行
- [ ] IAM ロール / ポリシーの権限変更
- [ ] 信頼ポリシー（AssumeRole）に外部アカウントが追加されていないか
- [ ] **一時セッションの取消**（キーを消しても、発行済みの一時認証情報は生きている）
- [ ] OS Login / プロジェクトメタデータの SSH 鍵
- [ ] **`startup-script` / `user-data`**
      ※ ここが汚染されていると、**インスタンスを再作成しても復活する**
- [ ] 監査ログ（CloudTrail / Cloud Audit Logs）が無効化されていないか
- [ ] ログ保存先バケットの変更・削除
- [ ] 未使用リージョンでのリソース作成

```bash
# AWS: 一時セッションの取消
aws iam put-user-policy --user-name <user> \
    --policy-name DenyOldSessions \
    --policy-document file://deny-before-now.json
```

## 10. 完了判定

以下がすべて埋まるまで「対応完了」としない。

- [ ] 進捗サマリの全行が「完了」
- [ ] クラウド IAM のチェックリストを**手で**実施した
- [ ] `startup-script` / `user-data` を確認した
- [ ] 新環境は、侵害環境を修正したものではなく、**信頼できるソースから構築した**
- [ ] 旧環境を破棄した（または隔離状態を維持している）

> [!IMPORTANT]
> **侵害済み環境を直して再利用することを標準にしない。**
> バックドアを消したつもりでも、見つけられていない永続化が残っている可能性がある。
